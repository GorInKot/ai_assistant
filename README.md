# Корпоративный ИИ-ассистент

Веб-приложение для сотрудников: единый чат с ассистентом, который отвечает по корпоративной базе знаний и работает с документами (Excel, Word, PDF).

> Оформление заявок (доступы, транспорт, обучение и др.) вынесено из ассистента: оно реализовано в корпоративном Портале, дублировать его здесь не нужно. Просьба «оформи заявку» в чате обрабатывается как обычный вопрос к базе знаний.

## Возможности

### Чат и база знаний
- ChatGPT-подобный интерфейс: тёмный сайдбар с историей бесед слева, область сообщений справа.
- Беседы сохраняются в БД на пользователя; переименование/удаление через сайдбар.
- Ответы на основе RAG по локальной базе знаний (`knowledge_base/`).
- **Гибридный поиск:** лексический BM25 + векторный (Yandex Foundation Models, опционально) с фьюжном через RRF.
- В каждом ответе — блок «Источники» со ссылками **открыть / скачать** для PDF/DOCX.
- **Цитаты и проверка обоснованности.** Ответ разбирается на утверждения, каждое сверяется с найденными фрагментами документов: найденным в документах подбирается дословная цитата (файл, страница), а утверждения без опоры (выдуманные числа, сроки, роли) выделяются предупреждением «проверьте». Проверка лексическая, работает без вызова модели (миллисекунды) и **не понимает смысл**: на тестовых «тонких подменах» (слова взяты из документа, факт перепутан) она пропустила 3 из 4, поэтому надпись в чате — «найдено в документах», а не «верно». Замер: `scripts/eval_grounding.py` (на реальных ответах локальной модели ложных тревог ≈5% утверждений, внедрённые выдумки ловятся в ≈99%).
- **Оценка ответов.** Под каждым ответом кнопки «👍 Полезно / 👎 Не полезно» (повторное нажатие снимает оценку). Оценки идут в аналитику пробелов в знаниях.
- Поддержка `MD`, `PDF`, `DOCX`, `DOC` (последний — best effort).
- Honest fallback: если в KB нет точной информации — прямо об этом сообщает.

### Файлы в чате
Файлы прикладываются к сообщению (скрепка у поля ввода), обработка идёт в памяти, на сервере файлы не сохраняются.
- **Файл без указаний — что это за документ:** ассистент называет вид документа (договор, акт, письмо, форма КС-2, спецификация, чертёж…), показывает, на чём основан вывод, номер и дату, и предлагает действия кнопками («Перевести в Word», «Извлечь реквизиты», «Составить реестр позиций»…). Сам ничего не делает — ошибка в виде безобидна. Подробнее — ниже.
- **Excel (.xlsx):** показать содержимое, сравнить две версии (в том числе бланки), объединить несколько с одинаковой структурой. Не похожие друг на друга файлы (мало общих заголовков и значений) не сравниваются — так и сказано; «сравни всё равно» — сравнить принудительно.
- **Word (.docx, .doc) и PDF:** выжимка (для PDF сканы распознаются).
- **Сравнение двух версий документа (Word, PDF, скан — в любом сочетании):** «сравни» → что изменилось по словам и числам, отчёт `comparison.docx`. Подробнее — ниже.
- **PDF → Word/Excel:** текст и таблицы в порядке страницы; сканы распознаются через OCR (Tesseract) с предупреждением.
- **PDF → реестр (Excel):** несколько документов (акты, счета, письма; до 10 за раз) собираются в одну таблицу по заданным полям: «составь реестр: номер, дата, подрядчик, сумма». Без перечня полей берётся стандартный набор. Каждое значение проверяется по тексту документа: чего в нём нет, подсвечивается жёлтым и попадает в колонку «Проверить»; если поле не найдено, ячейка остаётся пустой, а не заполняется догадкой.
- **Сканы спецификаций → реестр позиций (Excel):** «составь реестр спецификаций» + до 20 PDF (до 150 страниц за раз). Позиции всех спецификаций по форме ГОСТ 21.110 собираются в одну таблицу: шифр, файл, страница, раздел, позиция, наименование, марка, код, завод, единица, количество, масса, примечание. Подробнее — ниже.
- **Сравнение двух редакций спецификации (Excel):** два PDF + «сравни». Что изменилось по позициям (количество, единица, масса), что добавлено и удалено; если файлы не похожи на версии одного документа — так и сказано, сравнение не строится. Подробнее — ниже.
- **Поручения из записи IVA (демо-портал):** кнопка «Запись совещания» в `/protocol/` открывает выбор видео, аудио или стенограммы. После локальной обработки черновики со ссылками на фрагменты встречи проверяются и подтверждаются прямо в «Протоколе»; пункты видны также на `/tasks/`. Настройка — в `integrations/portal/README.md`; подключения к живой встрече и Outlook пока нет.

#### Что за документ (`app/services/doc_identify.py`)
Срабатывает, когда приложен один PDF или Word без текста (или со словами «что это», «посмотри»). Вид определяется по убыванию надёжности, и в ответе всегда сказано, на чём основан вывод:
1. **Форма бланка** — таблица спецификации ГОСТ 21.110 по геометрии граф (первые три страницы), без модели.
2. **Код унифицированной формы** (КС-2, КС-3, ТОРГ-12, М-29) — дефис в PDF бывает любым (мягкий перенос, неразрывный), это учтено.
3. **Заголовок первой страницы**: деловые документы сами называют себя («ДОГОВОР ПОСТАВКИ № 15», «Счёт-фактура», «ПРОТОКОЛ совещания»); заголовок — короткая строка с заглавной буквы в начале документа; рядом с ним ищутся номер и дата.
4. **Письмо** — по реквизитам («Исх. №», «Уважаемый…»); **чертёж** — по основной надписи («Изм.», «Кол.уч.», «№ док.», «Подп.»). Если есть и заголовок, и основная надпись, вид — по заголовку (основная надпись есть у любого документа проекта), а надпись упоминается отдельно.
5. Ничего из этого нет — вид оценивает локальная модель по началу текста, с пометкой «оценка модели, может ошибаться» (≈10 с).

Кнопки действий отправляют тот же файл с выбранной просьбой (файл хранится только в браузере до перезагрузки страницы). Замер на образцах с работы: 32 из 32 файлов — 28 спецификаций по форме таблицы, ведомость оборудования по заголовку, 3 чертежа изысканий по основной надписи; на выдуманных документах (письмо, акт, форма КС-2, договор, скан акта) — вид, номер и дата верны; 1–5 с на файл без модели.

По ходу найдено и исправлено для всех функций PDF: у чертежей из САПР кириллица в текстовом слое записана без таблицы кодировок («Èçì. Êîë.ó÷» вместо «Изм. Кол.уч»), причём на одной странице бывают и нормальные, и «сломанные» шрифты — такие слова перекодируются по одному (`repair_cp1251`; «530×8», «café» не трогаются). Листы больше A1 не рендерятся ради поиска формы спецификации, огромные сканы распознаются с пониженным разрешением (не больше 40 Мп) — иначе на 8 ГБ памяти опасно.

#### Реестр позиций спецификаций (`app/services/spec_registry.py`)
Языковая модель не участвует: система знает бланк.
1. Страница поворачивается по Tesseract OSD (сканы лежат боком), перекос выравнивается по длинным горизонталям.
2. Таблица ищется по пропорциям 9 граф формы ГОСТ 21.110 (OpenCV: вертикальные линии, допуск 2 % ширины, из 8 внутренних границ нужны 6); шапка подтверждается словами формы — так отсекаются листы регистрации изменений и титулы.
3. Тело таблицы — под строкой номеров граф «1…9»; разделители строк — сплошные и пунктирные линии.
4. Линии стираются, каждая графа распознаётся отдельно: количество и масса — только цифры, единица — построчно, со сверкой со словарём (однобуквенная «т»/«л» принимается, только если два прочтения сошлись: это частые ошибки чтения «шт»).
5. Строки собираются в позиции: многострочные наименования, количество на первой или последней строке, варианты «Д-160/Д-225» под общим наименованием, заголовки разделов.
6. Ничего не додумывается: правки от руки, цветные пометки у чисел, неуверенно прочитанные количество/масса/единица, не число в количестве — позиция выделяется жёлтым с причиной в колонке «Проверить». В размерах «114хб» буквы-двойники исправляются на цифры (только внутри размера).
7. Правки по документу: зачёркнутое значение заменяется новым («было …» в колонке «Правки по документу», голубая строка), целиком зачёркнутая позиция — серая, «исключена»; строки «в том числе» помечаются «В т. ч.», чтобы не посчитать количество дважды.
8. Самопроверка чисел: неуверенное число читается второй раз (увеличенным) — совпало, значит уверенное; но если у чисел есть чернила, не объяснённые текстом (штамп, рука, облако правки), позиция всё равно к проверке. Нечитаемая единица сверяется по картинке с уверенно прочитанными в том же документе (один шрифт и скан). Редкая для документа единица, отличающаяся от основной одной буквой («км» среди «м»), — к проверке. Цветная кайма сканера по краям букв отсеивается морфологией и не считается пометкой.

Замер на 29 настоящих спецификациях (28 сканов, разные институты и МФУ): 1945 позиций со 192 страниц за 7,7 мин (~2,4 с/стр.), ведомость оборудования (другая форма) отсеяна за 5 с; к проверке — 42 % позиций (в документах с рукописными правками и облаками изменений — до 70 %, в чистых — 2–5 %). Эталонная сверка глазами по сканам (7 листов, 69 позиций + 15 строк «в т. ч.»): без пометки принята 51 позиция (74 %), неверных количеств, единиц и масс среди них нет; неточности без пометки встречаются только в наименованиях (отдельные знаки, например «!» вместо «1»).

#### Сравнение редакций спецификации (`app/services/spec_compare.py`)
1. Обе редакции разбираются реестром позиций (см. выше); позиции, зачёркнутые целиком, в сравнении не участвуют.
2. Какая редакция старая — по именам файлов: номер редакции (`R03`/`R04`, `изм.1`/`изм.2`, `rC01`/`rC02`), слова «старый / новый» («исходный», «исправленный», old/new), даты (`01.10.2026`, `2026-10-15`). Если по именам не понять, ассистент **спрашивает кнопками** «Старая — …», а не угадывает по порядку приложения (от этого зависит, что попадёт в «добавлено», а что в «удалено»); можно и написать: «старая — первая», «новая — «имя файла»». Спрашивает только после проверки, что это версии одного документа, — разобранные файлы хранятся в памяти 15 минут, поэтому после ответа сканы не распознаются заново.
3. Позиции сопоставляются с сохранением порядка (максимум суммарного сходства): наименование и марка — с допуском на ошибки распознавания (латинские двойники, пропущенные буквы), номер позиции и совпавшее количество усиливают пару — так сопоставляется вариант, прочитанный в одной редакции полным наименованием, а в другой обрывком. Переставленные позиции находятся отдельным проходом (только почти совпадающие).
4. Сначала проверяется, что это версии одного документа: шифр по штампу совпал — да; иначе по содержимому (сопоставлено не меньше половины позиций меньшей редакции и у трети из них совпало количество). Разные документы одного проекта (похожие перечни, другие количества) так отсеиваются.
5. Статусы: «изменено» — единица, количество или масса различаются, и в обеих редакциях прочитаны уверенно; «проверить» — различие есть, но хотя бы одно значение прочитано неуверенно (правка от руки, штамп), позиция без пары прочитана неуверенно или по-разному прочитан размер в наименовании («114х5» → «133х5»); «добавлено», «удалено», «без изменений». Листы, у которых в другой редакции нет ни одной общей позиции, — «лист только в старой/новой»: изменение часто выпускают только на заменяемые листы, и это не добавленные позиции.
6. Результат — `spec_comparison.xlsx` (листы «Сравнение» с цветом по статусу и колонкой «Разница», «Сводка», «Как читать») и таблица изменений в чате.

Замер на настоящих образцах (две пары редакций): полная пара (4 листа, 55 позиций) — 15 «изменено», все 15 верны по сканам; 22 «без изменений» — все верны; остальные различия (в основном рукописные правки в старой редакции) — «проверить», ни одно настоящее изменение не потеряно. Пара «изменение на 2 листа против полной редакции на 12» — ложных «изменено» нет, 97 позиций отнесены к листам, которых нет в изменении. Две разные спецификации одного проекта распознаны как разные (у 2 из 34 сопоставленных позиций совпало количество). Время — 20–30 с на пару (распознавание сканов).

#### Сравнение версий документа по тексту (`app/services/text_compare.py`)
Для всего, что не спецификация: письма, договоры, акты — Word, PDF с текстом, сканы, в любом сочетании (например, подписанный скан против исходного Word). Два PDF сначала проверяются на форму спецификации — если обе спецификации, сравнение идёт по позициям (см. выше).
1. Слова берутся в порядке чтения: текстовый слой PDF, Word — абзацы и таблицы на своих местах (колонтитулы не входят), сканы — Tesseract с уверенностью по каждому слову. Перед распознаванием скана поворот определяется по OSD, линии таблиц стираются (иначе сетка читается как буквы и строки теряются); строки выстраиваются по положению на листе (сверху вниз, на одной высоте — слева направо), а не по блокам Tesseract — так порядок одинаков в двух сканах. Переносы «дого-/вора» склеиваются; номера страниц и колонтитулы, повторяющиеся на листах, отбрасываются.
2. Числа скана читаются второй раз: все слова с цифрами страницы вырезаются, увеличиваются и читаются одной полосой только цифрами; не сошлось — число неуверенное.
3. Сначала проверка, что это версии одного документа: доля трёхсловий меньшего документа, которые есть в другом (для коротких текстов — доля общих слов). Меньше 35 % — сравнение не строится («сравни всё равно» — принудительно).
4. Сравнение по словам (difflib): переверстанный абзац не превращается в десятки «изменённых строк»; регистр, знаки препинания, «1,5»/«1.5», латинские двойники букв не считаются различиями. Различия, разделённые одним-двумя общими словами, — один фрагмент.
5. Текстовый слой и Word точны — различие утверждается как есть. Рядом со сканом «изменено/добавлено/удалено» утверждается, только если на ошибку распознавания не похоже: короткая замена «по форме» (число на число, слово на слово) уверенно прочитанных слов с разным написанием, числа подтверждены вторым прочтением, либо связный фрагмент от 4 слов. Остальное — «проверить» с причиной (неуверенно прочитано, почти то же написание, латиница против кириллицы, фрагменты разной длины, короткая вставка — возможен пропуск распознавания).
6. Результат — таблица изменений в чате и отчёт `comparison.docx` («было» красным зачёркнутым, «стало» зелёным, с контекстом и статусом).

Замер: одинаковый текст против испорченного скана (наклон до 1,2°, размытие, шум, JPEG качества 30) — ни одного ложного «изменено» на всех уровнях порчи, все правки (числа, новый пункт) найдены. На настоящей паре сканов-таблиц (редакции одной спецификации) — 7 «изменено», все 7 верны по сканам; остальные различия — «проверить» (для таких документов есть сравнение по позициям). Версии одного документа — 42–46 % общего текста, разные документы одного проекта — 6–21 %.

Excel: перед сравнением двух таблиц проверяется, что это версии одной таблицы (не меньше половины общих заголовков колонок или 30 % общих значений), бланков — 40 % общих надписей и значений; какая версия старая — по именам файлов, иначе ассистент спрашивает (как для спецификаций, см. выше; так же для текстов).

Безопасность Excel-вывода: текст из внешних документов (PDF, чужие таблицы, имена файлов) записывается в `.xlsx` как обычный текст и никогда не становится формулой (защита от formula injection: `=HYPERLINK(...)`, `=WEBSERVICE(...)`, DDE), см. `append_row` в `document_processing.py`.

### Аналитика пробелов в знаниях
Страница «📊 Пробелы в знаниях» (admin и manager) показывает владельцу базы, чего сотрудникам не хватает в документах. Основа — журнал вопросов к базе знаний (`qa_log`): что спросили, нашёлся ли ответ, сколько утверждений без опоры в документах, по каким документам строился ответ, оценка «полезно / не полезно». Журнал живёт отдельно от бесед и не теряется при их удалении; имена и почты в отчёт не попадают, только подразделение.
- **«В базе нет ответа»** — темы, по которым ассистент ответил отказом (даже если пользователь поставил «полезно»: так благодарят за честный ответ, а потребность остаётся) или попросил уточнить вопрос, а ответа после этого так и не последовало: что дописать.
- **«Документ есть, но ответ не помогает»** — ответы, оценённые как «не полезно»: что доработать.
- **Документы:** те, по которым чаще всего ставят «не полезно», и те, что ни разу не использовались (при ≥20 вопросов за период).
- Сводка: вопросов, сколько сотрудников спрашивали, доля отказов, доля «полезно» среди оценённых, ответы с неподтверждёнными утверждениями. Выгрузка в Excel (`.xlsx`).
- **Считаются разные сотрудники, а не повторы:** тот, кто переформулировал вопрос трижды, — один человек.
- **Как объединяются похожие вопросы.** Сначала сравниваются «предметные» слова вопроса (без «как», «оформить», «порядок»), эмбеддинги подтверждают пересказы другими словами. Одних эмбеддингов мало: на `qwen3-embedding:0.6b` шаблонные вопросы вроде «Как оформить командировку?» и «Как оформить отпуск?» близки на 0.74–0.77, поэтому пороги подобраны так, чтобы лучше не объединить два похожих вопроса, чем слить разные темы (на размеченном наборе — 0 ложных слияний; часть настоящих пересказов остаётся отдельными строками). Без эмбеддера работает только по словам.
- Оценка и отказ — косвенные признаки: отчёт указывает, где искать проблему, а решает человек.

### Замер времени (страница «⏱ Замер времени», admin и manager)
Секундомер для расчёта эффекта: одна и та же задача (перенос листа спецификации в Excel, сравнение двух редакций, поиск ответа) выполняется вручную и с ассистентом на сопоставимых документах (`app/services/timing.py`).
- Ведущий выбирает участника (код, не ФИО), задачу, документ, тип (чистый скан / с правками / текст) и режим, жмёт «Старт» и «Стоп»; «Сбой — не считать» исключает замер из сводки. Над чатом в это время — плашка с секундомером.
- **Машинное время набегает само:** пока идёт замер «с ассистентом», время обработки вопросов и файлов ведущего прибавляется к замеру; время человека = всё время − машинное.
- После «Стоп» вносятся результаты сверки с эталоном: листов, позиций, помечено «Проверить», неверных значений, пропусков, лишних позиций; для сравнения — пропущенные и ложные изменения.
- **Сводка** — медиана на единицу работы (лист, пару, вопрос) вручную и с ассистентом, экономия в секундах и процентах. **CSV для Excel** (точка с запятой, запятая в дробях, кириллица без настроек; текст, похожий на формулу, не исполняется) — для пересчёта в часы, ставки и рубли.
- Каждый ведущий видит только свои замеры.

### Закрытый контур
- **Модели только внутри контура** (`app/netguard.py`): при старте адреса языковой модели и эмбеддингов проверяются — эта машина, частные диапазоны IP или имена из `INTERNAL_HOSTS`. Адрес вне контура (в том числе пустой адрес при заданном ключе — тогда клиент OpenAI пошёл бы в облако по умолчанию, и облачные эмбеддинги Yandex) — модель отключается с ошибкой в журнале. Разрешить внешние модели можно только явно: `ALLOW_EXTERNAL_MODELS=1`.
- **Проверка автономности:** `myenv/bin/python scripts/check_offline.py` — на настоящей конфигурации и локальных моделях перехватывает все сетевые соединения процесса и проходит путь сотрудника (вопрос по базе знаний с поиском, эмбеддингами и ответом модели; документ без пояснений; выжимка; сравнение версий); всё, что не к этой машине, блокируется и попадает в отчёт. Отдельно снимаются соединения процессов Ollama и сервера ассистента. Итог на ноутбуке разработки: «внешних соединений нет». Автотест того же — `tests/test_offline.py` (в том числе разбор скана спецификации).

### Ассистент в корпоративном портале
Раздел-плитка «ИИ-ассистент» портала `portalrnsk` с единым входом: одноразовый подписанный пропуск на 60 с (HMAC-SHA256), роль из портала, файлы портала не меняются — см. [integrations/portal/README.md](integrations/portal/README.md). Вторая плитка — «Конструктор и чертежи», вход по тому же пропуску.

### Кнопка ассистента на страницах портала (`widget.js`)
Круглая кнопка в правом нижнем углу каждой страницы портала (включая СИЗ) открывает справа панель с компактным ассистентом, не уводя со страницы. Вход — тем же одноразовым пропуском портала, при каждой загрузке панели; состояние панели и беседа переживают переходы по страницам. Портал не меняется: надстройка дописывает строку со скриптом в HTML-ответы для вошедших; в настоящем портале — одна строка в `base.html`. Подробно, с инструкцией для коллег, — [integrations/portal/README.md](integrations/portal/README.md#кнопка-ассистента-на-всех-страницах).

### Ассистент видит страницу портала
Вопрос из панели уходит вместе с тем, что открыто на странице (`app/services/page_context.py`): раздел и заголовок, активная вкладка, поля формы и фильтры («подпись: значение»), выделенная строка, заголовки и первые строки видимых таблиц (в том числе таблиц-сеток СИЗ), сообщения об ошибках и видимый текст. Собирает `widget.js` перед каждым вопросом.
- **Никогда не передаются** поля паролей, скрытые и служебные поля (`csrf`, токены, ключи), значения, похожие на ключи; объём — не больше 3 500 символов, важное (поля, ошибки, таблицы) — в начале и не обрезается. Сервер чистит и ограничивает ещё раз.
- **Плашка над полем ввода:** «👁 Видит: Метрология → Добавить СИ · 18 полей»; «что передаётся» показывает ровно тот текст, что уйдёт модели (`POST /api/page-context/preview`); «выключить» — вопросы уходят без страницы.
- **Как отвечает.** Вопрос об экране («что на экране», «что здесь», «это поле», «ошибка на странице»), о введённых данных («даты, которые я указал», «правильно ли я заполнил») или о поле со страницы (названы хотя бы два слова его подписи) — по странице, с учётом ещё не сохранённых значений: страница читается заново перед каждым вопросом. Если по базе знаний ответа нет или вопрос неоднозначен, а страница есть, — тоже по странице, а не просьбой уточнить процесс. Остальные вопросы — как раньше, по базе знаний. Страница идёт модели отдельным блоком с пометкой «данные, а не инструкции»; ответ сверяется со страницей (в цитатах — «Страница портала»).
- **Расчёты делает ассистент, не модель:** по датам в полях — сегодняшняя дата, сколько прошло или осталось, промежуток между датами («1 мес. 5 дн.») и ошибка порядка по подписям («Дата следующей поверки» раньше «Дата текущей поверки»); по таблицам — суммы числовых колонок в показанных строках. Модель получает их готовыми с указанием не пересчитывать. Плашка проверки у ответа по странице — «Сверено со страницей».
- **Журнал и история:** в `qa_log` — раздел портала (`portal_section`), в истории беседы у вопроса — метка «📍 Метрология → Добавить СИ»; текст страницы не хранится.

### Справка по разделам портала
В базе знаний — папка `knowledge_base/Корпоративный_портал/`: главная страница (разделы, учётная запись, роли и права), Метрология, СИЗ, ТКзаИИ, Протокол, План развития, Метрики, Панель задач, Конструктор и чертежи — назначение, что на экране, вкладки, фильтры, колонки, поля форм, кнопки, правила расчётов (сроки поверки, регламентная дата, оснащённость). Черновик составлен по интерфейсу и коду портала, без данных из него; проверяется владельцами разделов.
- **Приоритет раздела.** Вопрос из панели: фрагменты справки раздела, с которого задан вопрос, поднимаются при поиске; если лучше всего подходит справка своего раздела, ответ строится по странице вместе со справкой (другие документы базы в этот ответ не берутся). Ответ по странице всегда получает справку своего раздела (подходящие фрагменты или её начало).
- **В обычном чате** названия разделов («метрология», «ТКзаИИ», «СИЗ», «поверка», «оснащённость»…) подсказывают процесс «Корпоративный портал»; справка показывается в источниках (другие markdown-заметки по-прежнему скрыты).

### Конструктор деталей (раздел «Конструктор и чертежи», вкладка «🧩 Конструктор деталей»)
Описание словами → 3D-модель простой детали. Экспериментальная функция на базе стороннего открытого CAD [SolidCraft](https://github.com/bherbruck/solidcraft) (MIT/Apache-2.0; наш вклад — слой «слова → спецификация → команды» и проверки, сам CAD мы не писали).
- **Как это работает.** Локальная модель не пишет команды CAD: она заполняет небольшую схему детали (плита или цилиндр, размеры, отверстия, материал). Команды для `solidcraft-cli` строит наш код (`app/services/cad.py`), поэтому модель не может выдать произвольную команду — в CAD попадают только проверенные поля.
- **Проверки.** Спецификация проверяется до построения (отверстие за краем детали, пересечения, диапазоны размеров), а ошибка возвращается модели для исправления (до трёх попыток). После построения габариты и объём модели сверяются с аналитическим расчётом. Если размеров не хватает, ассистент задаёт уточняющий вопрос, а не придумывает значения.
- **Результат:** изометрия и вид сверху, габариты, объём, **масса по материалу**, файл STEP и скрипт команд. Вкладка «Редактор» — веб-версия SolidCraft, работает локально в браузере, в неё можно загрузить STEP.
- **Замер** (`ministral-3:3b`, 8 описаний на русском): 7 из 7 выполнимых описаний построены с первой попытки за 3–20 с, положения отверстий совпали с описанием; на описание без размеров («сделай кронштейн») модель задала уточняющий вопрос.
- **Что умеет.** Плита/блок и цилиндр со сквозными отверстиями (+ скругление углов, центральное отверстие, сетка и окружность отверстий), прямая труба (наружный диаметр и стенка) и **две трубы под углом** (косой стык по биссектрисе, углы 10–170°). Для стыка труб объём и габариты проверяются по замкнутым формулам: на углах 30–150° CAD совпал с расчётом по объёму в пределах 0,01% и по габаритам точно. Поля, которых нет в схеме, ассистент не отбрасывает молча, а показывает как «не учтено». Если просят то, чего конструктор не умеет (тройник, уголок, болт с резьбой, шестерня), он отвечает «Пока не поддерживается: …» и перечисляет, что можно построить сейчас; если не поддерживается только часть описания (фаски, резьба), деталь строится без неё и пропущенное показывается списком. Подмена одного предмета другим (кронштейн → плита) на замере встретилась один раз и закрыта примером в подсказке; на 4 вариациях запроса уже не повторяется. SolidCraft — молодой проект (v0.x, версия зафиксирована), бинарник из релиза не подписан.
- **История запросов.** Справа во вкладке список ваших запросов с исходом («построено», «нужно уточнить», «пока не поддерживается», «не получилось»). Из записи можно открыть деталь заново (она собирается из сохранённой спецификации за доли секунды, без модели), повторить запрос с правкой описания или удалить запись. История личная: каждый видит только свои запросы; хранятся описание, исход и спецификация, картинки и STEP не хранятся; на пользователя остаётся не более 200 последних записей.
- **Спрос на конструктор для владельца продукта.** На странице «Пробелы в знаниях» (admin и manager) и в выгрузке Excel есть раздел «Что просили построить, но это пока не поддерживается»: отказы «пока не поддерживается» и функции, которые пропущены при частичном построении (фаски, резьба). Формулировки модели объединяются в темы, считаются разные сотрудники и подразделения; имена не раскрываются. Это подсказка, что добавить в конструктор следующим. Названия пропущенных функций проходят очистку: размеры и пояснения в скобках, которые иногда кладёт в них модель, отбрасываются.
- **Установка.** `./scripts/fetch_solidcraft.sh` скачивает релиз v0.8.0 в `tools/solidcraft/` с проверкой контрольных сумм (macOS; в репозиторий бинарники не входят). Без них вкладка сообщает, что SolidCraft не установлен. Каталог можно изменить переменной `SOLIDCRAFT_DIR`.

### Чертёж трассы (раздел «Конструктор и чертежи», вкладка «📐 Чертёж трассы»)
Описание словами → эскиз плана трассы трубопровода (PDF и DXF). Экспериментальная функция на базе стороннего открытого 2D-редактора [CADCraft](https://github.com/storytold/cadcraft) (MIT/Apache-2.0, «AutoCAD на Rust»; чертёжный движок мы не писали). Устроена как конструктор деталей.
- **Как это работает.** Локальная модель заполняет небольшую схему: диаметр и стенка трубы, участки с длиной (м) и поворотом (влево — плюс, вправо — минус). Команды для `cadcraft-cli` строит наш код (`app/services/route_drawing.py`): лист A3, рамка, жирная линия трассы, номера узловых точек, размеры участков и углов (настоящие размерные объекты, редактируются в КОМПАС/AutoCAD), ведомость участков, условное обозначение, упрощённая основная надпись. Масштаб выбирается из стандартного ряда.
- **Проверки.** До построения: диапазоны длин и углов, не больше 12 участков, трасса не пересекает и не касается сама себя; ошибка возвращается модели для исправления (до трёх попыток). После построения: число размеров и узлов, всё в пределах листа, и **независимая проверка**: ломаная трассы читается обратно из сохранённого DXF, длины участков пересчитываются по масштабу и сверяются с заказанными (на примерах расхождение 0,000%).
- **Результат:** предпросмотр, список «как я понял описание», проверки, PDF, DXF и **DWG** (оба в версии R2000, самой совместимой: открываются в КОМПАС, nanoCAD, LibreCAD, AutoCAD); DWG читается обратно, состав объектов сверяется с DXF. Независимо проверено сторонней библиотекой `ezdxf` (DXF открывается без ошибок аудита, число объектов и тексты размеров верны); открытие DWG в настоящих КОМПАС/AutoCAD/nanoCAD не проверялось. Слои названы латиницей (FRAME, PIPELINE, DIMENSIONS, TEXT), а кириллица в подписях в версии R2000 записана кодами `\U+0422…`, которые AutoCAD и большинство программ показывают как буквы; вкладка «Редактор» — веб-версия CADCraft, работает локально в браузере (в ней можно открыть скачанный DXF). История запросов и ответ «Пока не поддерживается» (тройники, плавные отводы, профиль и т. п.) устроены как в конструкторе деталей; отказы попадают в раздел для владельца базы.
- **Замер** (`ministral-3:3b`, 10 описаний): все 10 дали ожидаемый результат (построено, «пока не поддерживается», уточняющий вопрос); один промах («…и ещё 14 м» по прямой) устранён, продолжение по прямой теперь допустимо.
- **Ограничения.** Это **эскиз плана**, а не проектный документ: без привязки к местности, отметок, пересечений, продольного профиля; рамка и штамп упрощённые, соответствие ГОСТ 2.104 и СПДС не заявляется. Только одна нитка из прямых участков с угловыми поворотами (без радиусов), труба показана условной линией. На коротких участках подписи теснятся. CADCraft молодой (v0.x), бинарник не подписан; версия зафиксирована.
- **Установка.** `./scripts/fetch_cadcraft.sh` скачивает релиз v0.6.2 в `tools/cadcraft/` с проверкой контрольных сумм (macOS; бинарники в репозиторий не входят). Каталог меняется переменной `CADCRAFT_DIR`. Без установки вкладка сообщает об этом. Из терминала: `python scripts/draw_route.py 12 8@90 10@-45 14@-45 --open`.

### Ролевая модель и админка
- Роли: `admin`, `manager`, `user`. Первый зарегистрированный пользователь получает `admin` автоматически.
- Страница «🔑 Пользователи» (для admin): таблица всех юзеров, переключаемые чипы ролей, сброс пароля, удаление.
- Самозащита: нельзя снять admin/удалить самого себя.
- Смена своего пароля через окно профиля.

### Аутентификация
- JWT-токены (60 минут).
- Все API-эндпоинты (кроме `/api/auth/*` и `/api/health`) требуют токен.
- `session_id` диалога префиксуется `u{user_id}:` — нельзя перехватить чужой контекст уточнения.

### Локальные модели (без внешних API)
Установить [Ollama](https://ollama.com) (`brew install ollama`) и запускать его с отключёнными облачными функциями, если требуется закрытый контур:
```bash

```
В другом терминале скачать модель эмбеддингов:
```bash
ollama pull qwen3-embedding:0.6b   # 639 МБ, размерность 1024
```
В `.env` задать `EMBEDDINGS_BASE_URL` и `EMBEDDINGS_MODEL` (см. выше) и перезапустить бэкенд. Первый запуск считает векторы всей KB (на M1 ≈ 12 минут для ~2400 фрагментов) и кэширует их на диск; кэш привязан к модели, при смене модели пересчитывается. Данные не покидают машину.

Для генерации ответов тот же Ollama подходит как LLM (OpenAI-совместимый API): `ollama pull ministral-3:3b`, затем `LLM_BASE_URL=http://127.0.0.1:11434/v1`, `LLM_MODEL=ministral-3:3b`, `LLM_REASONING_EFFORT=none`, `ENABLE_LLM_RERANK=0`.

Проверено на MacBook M1 / 8 ГБ ОЗУ, `eval/cases.json` (12 кейсов, реальная генерация):

| Модель | В памяти | Eval | Время на 12 кейсов | Замечания |
|---|---|---|---|---|
| `ministral-3:3b` | 2,5 ГБ | **12/12** | 11 мин (8–52 с на ответ) | рекомендуется |
| `qwen3.5:4b` | 4,3 ГБ | 10/12 | 25 мин | 3 ошибки нехватки памяти (OOM) |
| `qwen3.5:2b` | ~2,7 ГБ | 6/12 | 4 мин | часто отвечает «нет информации» |

Две модели в одном Ollama (эмбеддинги + LLM) на 8 ГБ работают, но запас по памяти небольшой: на время работы стоит закрывать тяжёлые приложения. Эмбеддинги: `qwen3-embedding:0.6b` (на этом eval — 9/0 против 8/1 у BM25).

## База знаний

Поддерживаемые форматы: `PDF`, `DOC`, `DOCX`, `MD`.

Структура: каждая папка верхнего уровня в `knowledge_base/` — отдельный процесс. Внутри рекомендуется `инструкции/`, `чеклисты/`, `faq.md`.

После добавления файлов:
```bash
curl -X POST http://127.0.0.1:8000/api/reindex \
  -H "Authorization: Bearer $TOKEN"
```

### Рекомендации
- Лучший retrieval — для `PDF/DOCX` с корректно извлекаемым текстом.
- Для `DOC` используется best-effort (если извлечение ненадёжно, файл не участвует в retrieval, но остаётся доступным как источник).
- `md` — для FAQ/глоссариев/правил. В блоке «Источники» в UI они скрыты (показываются только прикладные документы).
- Имена файлов: формы — `Форма_...docx`, инструкции — `Инструкция_...pdf`.

### Векторный поиск
Если в `.env` заданы `YC_API_KEY` и `YC_FOLDER_ID`, при `build()` индекса считаются эмбеддинги всех чанков (модель `text-search-doc`) и кэшируются в `logs/embeddings_cache.npz`. При reindex пересчитываются только новые/изменённые чанки (по `hash(chunk.text)`).

Запрос пользователя эмбеддится через `text-search-query`, считается cosine top-k, результаты сливаются с BM25 через RRF (`k=60`). Score в `RetrievalResult` остаётся в шкале BM25 (для корректной работы порогов `is_context_strong`), порядок — по RRF.

## Деплой (Render)

Проект собирается на Render как Docker-сервис: multi-stage [Dockerfile](Dockerfile) сначала строит React-фронт в Node-образе, потом кладёт `frontend/dist/` в Python-образ с FastAPI. Конфигурация в [render.yaml](render.yaml).

### Первый деплой

1. Render Dashboard → **New → Blueprint** → выбрать этот репозиторий.
2. В разделе **Environment** задать секреты (помечены `sync: false`):
   - `LLM_API_KEY` — Groq API key.
   - `YC_API_KEY`, `YC_FOLDER_ID` — Yandex Cloud Foundation Models (для hybrid retrieval; без них работает только BM25, но быстрее cold start).
   - `INITIAL_ADMIN_EMAIL`, `INITIAL_ADMIN_PASSWORD` — pre-seeded админ. Создаётся при каждом старте, если не существует, и закрывает дыру «первый зарегистрировавшийся = admin».
   - `JWT_SECRET` Render сгенерирует автоматически (`generateValue: true`).
3. После первого билда открыть `https://<your-service>.onrender.com` и залогиниться под `INITIAL_ADMIN_*`.

### База данных

`render.yaml` определяет блок `databases:` с free-Postgres `ai-assistant-db` (256 MB, 30-дневный срок жизни инстанса). Render автоматически подставляет connection string в env-переменную `DATABASE_URL`, и при первом деплое схема создаётся через SQLAlchemy `create_all`.

Это решает главную проблему free-плана: БД (пользователи, история чатов) переживает деплои и cold start. Локально остаётся SQLite (когда `DATABASE_URL` пуст, `app/db.py` использует `sqlite:///./app_data.db`).

Через 30 дней free-Postgres истекает — нужно пересоздать инстанс или апгрейднуться на платный план ($7/мес для Starter с persistent storage).

### Ограничения free-плана

- ⚠️ Файловая система эфемерная — теряются между деплоями/cold-стартами:
  - Embeddings cache (`logs/embeddings_cache.npz`) — пересчёт ~3 мин через Yandex API.
  - Логи запросов и действий (`logs/*.log`).
- БД (Postgres) — НЕ эфемерная, переживает деплои.
- Pre-seeded admin (`INITIAL_ADMIN_*`) создаётся только если в БД нет пользователя с таким email — после первого старта это no-op.
- Чтобы ускорить cold start: закоммитить `logs/embeddings_cache.npz` в репо (попадёт в Docker image), убрав его из `.gitignore` и `.dockerignore`.

### Прод-апгрейд (опционально)

Платный план Starter ($7/мес) + persistent disk 1 GB ($1/мес) добавляет персистентность логам и embeddings-кэшу:

1. В [render.yaml](render.yaml) раскомментировать блок `disk:`.
2. В Environment добавить:
   - `LOG_FILE=/data/logs/assistant.log`
   - `EMBEDDINGS_CACHE=/data/logs/embeddings_cache.npz`
3. `DATABASE_URL` менять не нужно — Postgres уже отделён.
