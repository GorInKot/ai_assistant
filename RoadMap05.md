# План-роадмап модернизации корпоративного ИИ-ассистента

**Дата составления:** 2026-05-26
**Конечная цель:** единый инструмент для работы сотрудника — чат с ассистентом, который покрывает все вопросы из загруженной базы знаний и умеет создавать заявки, направляя их ответственным.

---

## Зафиксированные решения

| Тема | Решение |
|---|---|
| UI-стек | Vite + React + shadcn/ui |
| Раздел «Законодательство РФ» | Гибрид: базовая статика + ручное обновление админом |
| База сотрудников — источник данных | Импорт из Excel/CSV |

---

## Анализ текущего состояния

**Стек:** FastAPI + SQLite (SQLAlchemy) + JWT auth + OpenAI-совместимый LLM (Groq/Ollama) + RAG над локальной KB + одностраничный HTML/JS UI.

**Ключевые модули:**
- `app/main.py` (1152 строки) — монолит: маршруты, бизнес-логика, регэкспы ролей, fallback, профиль, auth
- `app/kb.py` (1037 строк) — RAG-индекс с лексическим поиском (сильная сторона)
- `app/llm.py` — LLM-вызов и rerank
- `app/db.py` — модель `User` и заготовка `UserAction` (не используется)
- `app/actions.py` — заявки в `logs/actions.log` (JSONL), не в БД
- `app/profile.py` — единый профиль в `profile.json` (один на всех пользователей)
- `static/index.html` (1377 строк) — табы: Чат / Документы / Действия / Кабинет блока / Дашборд / ЛК

**Критичные изъяны:**
1. `ProfileStore` хранит один `profile.json` на всё приложение → все пользователи делят один профиль
2. Заявки в JSONL без `user_id`, без статусов, без назначения ответственного
3. Функция `get_profile` объявлена дважды в `main.py` (строки 1046 и 1146) — вторая перетирает первую
4. `/api/ask` не требует auth, `session_id` приходит с клиента (можно подделать)
5. `DialogStateStore` хранит состояние диалога в памяти процесса; после рестарта всё теряется

## Этап 4. База сотрудников и ответственных (3–5 дней) — пункт 4

**Решение:** базовый CRUD + импорт из Excel/CSV.

### Схема данных:
```
Employee:        id, user_id (опц.), full_name, email, position,
                 division, subdivision, phone, is_active
ResponsibilityArea:  id, name, slug, description
                 ("обучение", "медосмотр", "ЕКТП-заявки"...)
Responsibility:  id, employee_id, area_id, is_primary,
                 scope_division (опц.), scope_subdivision (опц.)
```

### API:
- `GET /api/employees` — список
- `GET /api/responsibilities?area=обучение&division=Уфа` — кто ответственный
- `POST/PUT/DELETE` — управление (для админа)
- `POST /api/admin/employees/import` — загрузка Excel/CSV (`openpyxl` для xlsx)

### Шаблон импорта:
```
email, full_name, position, division, subdivision, phone,
responsibility_areas (csv в csv: "обучение;медосмотр")
```
Upsert по email, лог пропусков для админа.

Опционально расширить `glossary.md` или добавить `knowledge_base/{раздел}/ответственные.md`, чтобы ассистент при ответе мог подмешивать актуального ответственного из БД.

## Этап 5. Заявки в чате через ассистента (5–7 дней) — пункт 5

**Цель:** intent-flow: «хочу на обучение» → диалог-уточнение → заявка → автоматическая отправка ответственному.

### Архитектура:

```
Сообщение в чате
       ↓
   Intent classifier (LLM с фиксированным набором интентов)
       ↓
   ┌─────────────┴──────────────┐
   ↓                            ↓
 RAG-ответ                  Action flow:
                          1. Слот-машина: какие поля
                             нужны для этого типа заявки?
                          2. LLM задаёт вопросы по
                             недостающим слотам
                          3. Слоты заполнены →
                             карточка подтверждения
                          4. Пользователь жмёт
                             "Подтвердить"
                          5. Заявка в БД +
                             email/уведомление
                             ответственному
```

### Реализация поэтапно:

**5.1. Таблицы:**
```
Request:      id, user_id, type, status, payload_json,
              assigned_employee_id, created_at, updated_at,
              conversation_id (откуда пришла)
RequestEvent: id, request_id, event_type, actor_id,
              comment, created_at
```

**5.2. Каталог типов заявок (YAML/JSON):**
```yaml
- type: training_request
  title: Заявка на обучение
  responsibility_area: обучение
  slots:
    - name: course_name
      question: На какое обучение хотите записаться?
      required: true
    - name: preferred_dates
      question: Какие даты предпочтительны?
      required: false
```

**5.3.** LLM-роутер интентов через structured output (как уже в `app/llm.py`).
Классы: `qa | request:training | request:medical | request:transport | anonymous_appeal`.

**5.4.** Slot-filling поверх существующего `DialogStateStore`. Расширить состояние: помимо `pending_question` хранить `pending_request` со списком незаполненных слотов.

**5.5.** Маршрутизация ответственному:
- При создании заявки берётся `responsibility_area` из каталога
- Запрос в `Responsibility` с фильтром по `division/subdivision` пользователя
- Найденный сотрудник = `assigned_employee_id`
- Уведомление: email через SMTP (минимум) или интеграция в корп.мессенджер

**5.6.** Анонимные обращения — отдельный тип заявки без `user_id`, фиксированная роль-получатель (например, «комплаенс»).

### Открытые вопросы:
- Каналы доставки (email / мессенджер / тикет-система)?
- Веб-страница для ответственного по управлению входящими или достаточно ссылки в письме?
- SLA по типам заявок?

## Дополнительные технические работы (вне списка пользователя, но критично)

1. **Vector search.** Текущий BM25-подобный retrieval работает на ~50 документах. При добавлении законодательства РФ релевантность просядет. Миграция на FAISS/Chroma + эмбеддинги.
2. **Миграции БД.** Сейчас в `app/db.py` ручной `ALTER TABLE` через `PRAGMA`. Завести `alembic`.
3. **Тесты.** Добавить `pytest` + smoke-тесты на auth и `/api/ask`.
4. **Render деплой.** SQLite-файл на эфемерной FS Render free tier — данные теряются. Миграция на Postgres перед прод-использованием.
